# 静默失败排查法(没有报错的时候最难查)

**触发条件**:命令 rc 非 0 但一行输出都没有;套件跑到一半退出且不打印结论行;"改完了但行为没变";"全绿却像少了什么"。

本项目这几天里同族事故连发四五次,**每一次的真凶都不是判据本身**,而是"报错被吞"或"东西没被装载"。所以顺序不能反。

## 第 1 步:先把报错弄出来(不要跳过)
最常见的是被重定向吃掉了:
```bash
# 只读那一句,去掉 >/dev/null 2>&1 单独跑,或临时把套件里那行的重定向删掉
grep -n '>/dev/null 2>&1' <出问题的脚本> | head
```
本项目实例:回归表跑到 `path_access` 那一段就 rc=1 退出、**不打印结论行**,一条 FAIL 都没有。原因藏在
```bash
path_access "…/probe.txt" rw "写入" >/dev/null 2>&1     # ← 报错在这里被吞
```
把重定向临时去掉,立刻看到 `line 97: auto_session_id: unbound variable`。**没有这一步,后面所有猜测都不可靠。**

## 第 2 步:确认"跑完了"还是"跑到底了但结论丢了"
看有没有约定的机器可读结论行:
```bash
bash <套件>; echo "exit=$?"            # rc≠0 且没有结论行 = 中途死亡,不是断言失败
```
本项目刻意把结论行做成**无色彩、固定字段**(`RESULT …` / `PASS=… FAIL=…`),就是为了能被 grep 到 —— 靠"能不能 grep 到结论"来判断套件是否跑完,本身就是一次需要被钉住的假设。

## 第 3 步:查"东西有没有被装载"(bash 项目的头号假绿来源)
| 症状 | 真凶形状 |
|---|---|
| `unbound variable` 但源码里明明赋值了 | 赋值行含命令替换,被夹具的抽取过滤器排除(注意 `$(($((` 这类**算术**派生同样以 `$(` 开头,容易被一起误排) |
| 判据永远不命中,像"规则失效" | 新增全局用了不被名字白名单识别的前缀(如 `CTX_`/`POLICY_` 这类新前缀)⇒ 半装载 |
| 报"命令不存在:[X]" | 函数没进夹具的显式抽取名单 |
| 函数被抽成半截 | 抽取用 `grep '^name='`,对 `+=` 行、跨行赋值不匹配 |
| 报错行号离真凶几十行远 | 错误发生在 `eval` 进来的代码里,bash 归因到 eval 那一行 |
**通用处置**:报错提到某个名字时,先 `grep -n '^名字=' 源码` 确认它是否**真的会被装载**,再怀疑逻辑。

## 第 4 步:查"你以为改了,其实改的是另一份"
本项目实例:盘上判据实测对某条命令返回"不拦",而运行中的会话拦了 ⇒ 不是判据错,是**进程内存里是旧代码**(bash 惰性读文件,老会话不会自动跟上)。两条硬办法:
1. 结论行里带源码 sha(`src=…`),两次运行 sha 不同就是源码变了;
2. 审计行带生效版本(`pol`),不一致直接退回人工。
**在没有版本证据之前,不要下"判据写错了"的结论** —— 这是本项目花过最多时间的一次弯路。

## 第 5 步:检查注释里的行号/文件名是否已过期
本项目有一次照着注释 `grep '^_compat_isbash32=…'` 找了二十多分钟:那个名字早已改成运行时判定,赋值行根本不存在。**注释是线索不是证据**:顺着注释找东西时,先 `grep -n '关键名' 文件` 确认它还在。

## 第 6 步:被吞掉的"成功"
`git add a.txt README.md 2>/dev/null` —— 只要有一个路径不存在,**整条 add 一个文件都不加**,而错误被 `2>/dev/null` 吃掉,现象是"提交时提示 nothing to commit"。规则:
- 不要用 `2>/dev/null` 包住任何**写操作**命令;
- 关键动作之后必须跟一次可观察的验证(`git status --porcelain`、`-e` 判存在、读回内容),而不是"看起来没报错"。

## 最后一句
这类 bug 的共性是**证据被主动或被动销毁**。修完之后请顺手做一件事:把那个被吞的报错变成一条断言(红条会自带解释的那种),否则同一形状一定还会再来。
