# 技能撰写规范(本 harness 的实测口径)

**触发条件**:你要新增技能、改技能、或觉得"这条经验应该记下来"。

## 装载事实(先记住这四条,它们决定写法)
1. **常驻上下文的只有 `name` + `description`**;正文要模型主动 `read_skill` 才拿到。所以 description 是**唯一的触发面**,正文再好,不触发等于不存在。
2. `SKILL_DESC_MAX=200` 走的是 `clip_line_width`,它按**字节宽度**计数(ASCII=1、汉字=3)⇒ **中文描述实际预算约 66 个字,超了从尾巴开始砍**。重要信息必须往前放,"不适用"这类边界能省则省。
3. `SKILL_MAX_INJECT=30` 是注入上限;但真正的天花板是注意力 —— 建议**常驻 10 条以内**。
4. 技能目录里的**符号链接一律被跳过**(注入侧与读全文侧两处都堵)。所以不要用软链接"共享/复用"技能,那只会让它静默消失。

## description 怎么写
- **场景导向**,不是主题导向:
  - ❌「调试技巧」
  - ✅「命令被硬墙拦下(H1–H14)时查:这条守什么、合法出口是什么;撞墙后不要改写路径重试」
- 把**最可能被搜到的词放在前 30 个字**(截断只砍尾巴)。
- 允许写"负面触发"("不适用 X")只有当预算够;不够就删,别为了格式牺牲触发词。
- 不要放数字、路径、版本号:那些会漂,漂了 description 就永久误导(而且它每次请求都在上下文里)。

## 正文结构(按这个顺序)
1. **触发条件**重复一句(双重保险:模型读正文时先确认"我现在该不该用它")。
2. **铁律 / 一句话规矩**(可执行的那种,不是价值观)。
3. 步骤或速查表(表格优于散文;命令必须能直接复制)。
4. **不适用 / 边界**(防止它被过度套用)。
5. 长度:60-80 行内。超了就拆,把细节挪到 `references/*.md`,正文只留"什么时候去读它"。

## 会变动的数字怎么放
写"当前实跑值(2026-08-07):535 条;**以命令输出为准**"。既给读者一个预期,又不让技能变成过期事实的来源。绝不写"永远是 535"。

## 不该做成技能的四种东西
| 不该放 | 为什么 | 该放哪 |
|---|---|---|
| 红线判据("不许 rm -rf ~/") | 技能是**模型可能不读**的软知识,红线不能靠纸条 | 硬墙规则 + 闸门断言 |
| 必须每次生效的流程 | 同上:触发不确定 | 脚本 / 启动检查 / 提交校验 |
| 环境事实(版本、IP、PAT、路径) | 会漂,漂了比没有更坏 | 配置文件 |
| 一次性事故复盘 | 除非它给出**可复用的判断**;否则那是日志 | 审计日志 / 提交信息 |

判断口诀:**能被"忘记读"影响的后果有多大?** 后果是"多花十分钟"→ 技能合适;后果是"环境被破坏/凭据外泄"→ 必须是判据,不能是技能。

## 数量与淘汰
新技能上线后过一段时间查一次:`read_skill` 有没有真的调过它。长期没人调用的技能只有两种解释 —— 触发词写坏了(改 description),或者它不该存在(删)。留着不触发也不删,就是在给未来的自己制造注意力税。

## 落地流程(会被自家规则拦,是有意的)
模型往 `~/.ct/skills/` 写会被 H5 拒 —— 防的就是运行时自己长技能。正确姿势:
1. 在仓库里起草:`<工作目录>/skills/<name>/SKILL.md`;
2. 用 README 里那条校验 snippet 检查 frontmatter 与 description 字节数;
3. **人**手工 `cp -R skills/<name> ~/.ct/skills/`;
4. 新会话里用自然说法问一遍,确认它能被触发。
