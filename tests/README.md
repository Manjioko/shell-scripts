> **流箱终端可移植性基线(2026-10,修 Terminal.app 阶梯重复)**
>
> **现象**:macOS 自带 Terminal.app 里,流箱把同一段文字画成"每行一遍、每行缩进递增"的阶梯;
> 同一份字节流在 Ghostty 里完全正常。
>
> **实测归因**(`tests/termcap_probe.py` 在目标终端里发 DSR 实测,不改任何东西):
>
> | 能力 | Ghostty `xterm-ghostty` | Terminal.app `xterm-256color` |
> |---|---|---|
> | `CSI s` / `CSI u`(存/取光标) | PASS | **FAIL** ← 根因 |
> | `ESC 7` / `ESC 8` | PASS | PASS |
> | `ESC[?7l`(关自动换行) | PASS | PASS |
> | `autowrap` / 裸 `LF` 隐含回车 | PASS | PASS |
>
> 流箱的锚点机制正好就是那唯一一项不认的:存光标失效 → paint 从上次落点继续写、
> close 擦不回箱顶 → 内容在屏幕上越走越偏。**字节流形状不变,所以只能看屏幕**。
>
> **顺带排除**:曾怀疑 `tty.setraw()` 清 `OPOST` 使 `\n` 只下移不回列。查调用点 —— `term.py` 的
> `raw_mode` **目前无任何调用者**,流式时 `ONLCR` 仍开着;探针 `LF=CRLF=PASS` 也印证了。
>
> **改法**:位置自己记账(`drawn` 行数 + `\r` + `ESC[nA` **相对**回位),每行再按终端宽度硬截断
> (不认 `?7l` 也不会折行,行数记账才成立)。`?25l/?7l` 照发但不再是正确性前提。
> **不用 `ESC 7/8` 替代**:它存的是**绝对行号**,屏幕一滚就失效(流箱画在屏幕底部必然滚),
> 相对移动没这个毛病 —— 所以是"彻底不存",不是换个存法。
>

> | 指标 | 数值 |
> |---|---|
> | main 调用 | 67 次,合计 prompt **1765 万 token** |
> | 最后一条上下文 | **1107 条消息 / 565 KB / 35 万 token** |

>

> 压下来了(便宜≠免费),一次缓存失效就按全价重算,而且 35 万 token 的 prompt
> 本身拖慢首字延迟。
>
> ### 决定:不折叠工具结果
>
> 我实现过一版 `_age_tool_results()`(把较早的 tool 结果折成"头部 + 折叠说明",
> 实测能把模拟会话从 572K token 压到 38K),**已按用户判断完整撤回**。
>
> 理由(记下来,免得以后有人"顺手再实现一遍"):
> - 折叠的本质是**让模型看不见它自己刚做过的事**。省下的 token 是显性的,
>   代价是隐性的:模型可能重复执行已经成功的命令、基于残缺输出做出错误判断、
>   或者干脆要求"重跑一遍" —— 那样反而**多花**一次完整请求。
> - 这个项目的失败模式已经反复证明:**静默的信息丢失比多花 token 贵得多**
>   (见"安装包漏文件""venv 断链静默跳过"几条)。工具输出属于"模型的可信记忆",
>   不该由一层启发式规则替它裁剪。
> - 真要省,更该动的是**工具数量**(schema 固定成本)和**压缩阈值**,而不是历史内容。
>
> 因此 `上下文体积` 闸门保持 **26/26**,不含任何折叠相关断言。
>
> ### 顺带确认的两件事(都不是 bug)
> - **鉴权没有把会话发给 AI**:初审 = AUTH_SYS(2532B)+ 命令;终审 = AUTO_FINAL_SYS(659B)
>   + 命令 + 自述理由。34 次 auth 合计才 2.5 万 token(0.1%)。
> - **压缩不触发是设计如此**:`CTX_WINDOW` 默认 100 万、阈值 75 万;35 万离触发还远。
>   想更早压缩就调小 `TOKEN_THRESHOLD`(比如 `50000`),这是**用户可控**的,
>   比自动裁剪历史更透明。
>
> ### 保留的改动:修监控自身被测试污染
> 账本里曾有 24 条 `prompt=0` 的记录,全是 `msgs=1 bytes=4`、`think: enabled` 的形状 ——
> 是**闸门测试**打进来的(测试用 `127.0.0.1` 桩端点)。危害不是多几行垃圾:
> A5 判据会对它们全线报警,看着像产品缺陷。

> **工具参数校验(2026-10,从一次"命令输出为空很奇怪"追出来的 bug)**
>
> 现场:界面上出现两次
>
> ```
>  ⏺ shell ·
> └─ 完成 · 共 0 行 ┘
> ```
>
> 于是模型判断"命令输出为空很奇怪,可能是工具的输出问题",**白烧一轮**去 read_file 排查。
> 真因不是输出:`run_shell_command` 拿到的是 `{"command": ""}` ——
> `bash -c ""` 本来就返回 0 行、rc=0,于是显示"完成",返回空字符串。
> **一串"成功"的假象,只有"内容为空"这一个可疑线索。**
>
> 同类形状(都不报错):`read_file {"path": ""}` 读到工作目录本身、
> `write_file` 缺 `content` 写空文件、`grep {}` 扫全树、`web_fetch {}` 去抓空 URL。
>
> 而 `tools_spec.json` 里 `required` 声明是**齐全的**(每个工具都写了)——
> 问题是从没人校验它。声明了没人执行,等于没有。
>
> **根因是移植漏了一处兜底**(用户问"master 从来没见过这个错,是不是没对齐" —— 是):
> ```bash
> # master: legacy_wchat.sh:7331,run_shell_command 分支的第一件事
> command=$(jq -r '.command // empty' <<< "$fn_args")
> if [[ -z "$command" ]]; then
>     content="错误:命令参数为空,工具调用参数解析失败: ${fn_args:-"(空)"}"
>     add_message "$content" "tool" "$fn_id"; continue
> fi
> ```
> master 每个工具分支都对取值做了 `// empty` 兜底并在执行前判空;Python 版把
> `cmd = a.get("command") or ""` 取空之后**直接就往下执行**了。这条兜底是
> "把 jq 的写法照搬过来,但丢掉了它后面那道判空"的典型 ——
> **迁移时只搬了取值,没搬取值之后的守卫。**
>
> 所以现在两件事都做:
> 1. **措辞与 master 逐字对齐**(`错误:命令参数为空,工具调用参数解析失败: …`),
>    那条原文是排障时的搜索锚点,不该被"统一措辞"改掉;
> 2. 校验**上提到 `_run_tool` 入口**,覆盖全部工具(不只 shell),以 `tools_spec.json`
>    为唯一真源 —— master 是每个分支各写一遍,Python 版有集中入口,就不该重复。
>
> 改法(`_run_tool` 入口,所有工具统一过一遍):
> - `_required_of()` 从 `tools_spec.json` 读必填清单(**唯一真源**,不在代码里抄第二份);
> - 缺失/空串/纯空白 → 立刻返回 `错误:<工具> 缺少必填参数 X(收到的参数:…)`,
>   **不透传去执行**;报错里要求"重新发起这次调用",并回显收到的参数便于排查;
> - 坏 JSON 的报错**回显原文片段**(以前只说"不是合法 JSON",看不到是什么);
> - 非对象 JSON(数组/标量)也拒;
> - 横幅:空命令显示 `⏳ (命令为空 —— 本次调用未带 command 参数)`,**不许留一片空白**
>   —— 留白会被误读成"命令很短"。
>
> 闸门 `工具参数` **32/32**(含 3 条 master 对齐锁:shell 原话仍在、非 shell 不硬套、
> master 源码里那句兜底没被删)。变异各自被杀:去掉校验(退回原 bug)→**9 红**;
> 横幅退回留白→2 红;校验挪到工具分支之后→1 红(结构锁);去掉 master 原话→1 红。
> 正向反锁:正常命令仍能执行、`list_dir` 无必填所以空参仍放行、非 shell 横幅不受影响。

> ### 1. index 缺省值(这才是"凭空出现空参数"的真因)
>
> ```bash
> # master: legacy_wchat.sh:7720
> t_idx=$(printf '%s' "$tpiece" | jq -r '.index // 0' 2>/dev/null)

> **UTF-8 完整性基线(2026-10,回答"输出出现乱码")**
>
> 用户报:`tail -c 200 x.log | cat -v | tail -2` 的输出里出现 `^[[1m�M-^TM-^@…` 一堆乱码,
> 怀疑解析错了。**复现结论:不是 wchat 的 bug。** 两个原因都在命令本身:
> 1. `tail -c 200` 按**字节**切,正好落在多字节字符中间 → 输出开头就是非法 UTF-8;
> 2. `cat -v` 把 >=0x80 的字节转成 `M-^T` 表示(这是它的职责)。UTF-8 locale 下它会把
>    **合法**序列原样放过、把**非法**的逐字节转义 —— 于是屏幕上出现"合法中文 + `M-^T`"
>    混排,看着像解析错误。
>
> wchat 用 `errors="replace"` 解码,非法字节显示成 `�` —— 那是**忠实反映输入非法**。
> 正确用法:`tail -n`(按行)而不是 `tail -c`(按字节);看 UTF-8 文本别用 `cat -v`。
>
> **但要留一道闸门**:这个项目里"按字节截断"到处都是(`clip_bytes` / `truncate_output` /
> 头尾省略 / tty 分块读取),任何一处多字节字符中间下刀都会产出同样的乱码,而症状与
> "命令选错了"完全一样 —— 下次真出问题就没人信了。所以新增 `UTF8完整性` **24/24**:
> 1. 合法 UTF-8(CJK/emoji/组合字符/生僻字/多行)过 `truncate_output`(10 档列宽 × 4 档行数)、
>    `clip_bytes`(9 档字节上限)、`clean_line`(5 种控制符混排)→ **不许出现 U+FFFD**;
> 2. **非空转自检**:非法字节必须变成 U+FFFD —— 否则第 1 条可能只是"检查永远返回 0";
> 3. **结构锁**:pty 必须 `b"".join(chunks)` 后一次性解码。**逐块解码是最典型的引入方式**
>    (os.read 的 65536 边界随时劈开一个中文字符),变异成逐块解码 → 2 红;
> 4. 责任归属:`tail -c N`(N 由搜索确定,切在多字节中间)必出非法 UTF-8,而
>    `tail -n` 与整读是合法的 —— 把"这是命令的问题"变成可复核的断言。
> 另一处变异:把 `_clip` 退回 `line[:maxb]` 硬切 → 8 红。
>
> ⚠ 顺带修了自己的一个事故:`run_gates.sh` 的五个数组被我改得不**等长**
> (NAMES/CMDS/NOTE=58、MODE/PAT=59),那会让闸门**整体错位**。现在已核到全 59,
> 并把这个检查当成改闸门表后的必做项。
